# Code Quality & UI Modernization Plan

Living plan for bringing the codebase in line with Laravel best practices and migrating the UI to Tailwind CSS v4. Work it top to bottom, one phase (or one batch inside a phase) at a time, and tick items off as they land.

**Status legend:** `[x]` done · `[ ]` to do · `[~]` in progress · `[-]` deferred

**Rules for every batch**

- Keep each batch small and independently shippable: one concern, its tests, green suite.
- Behavior must not change unless the item says so. Existing tests are the safety net; add tests where a fix changes or protects behavior.
- Definition of done: `vendor/bin/pint --dirty --format agent`, the full suite passing (`php artisan test --compact`), `npm run build` if frontend files changed, and this file updated.

Add a Phase 3 item for it (and consider running the sync on writes or in a job rather than on every page view)? **Decided 2026-10-21:** move the sync off page views; added as a Phase 3 item.

The full suite went from about 22 s to 35 s. Accept it, or fake the job by default in the base `TestCase` and run it only in the notification tests?
- [ ] `ExportLifecycleService::reconcileStale()` skips all stale-export repair while the `jobs` table has any row. Participant notification jobs now land in that table on every progress write, so the repair on the dashboard is skipped until the queue worker (`queue-cron.sh`, `--stop-when-empty`) drains them. Scope the check to export jobs (or to the export queue)?
- [ ] The dashboard's mock-interview partner list still calls `WeekProgressionService::canAccessWeek()` / `isWeekPassed()` per Week 4 pair (about 3 queries per pair). Pairs are few, so this was left as is; batch it if pairs grow.
- [ ] `resources/css/app.css` contains `p[id="mentor-interview-timezone"] { display:none; }`. It became active when the layout started loading `app.css`, so the timezone line on the Week 4 submission page is now hidden. Confirm that it should stay hidden, or remove the rule.
- [ ] `APP_NAME` in `.env` / `.env.example` is still `Laravel`, so outgoing mail uses "Laravel" as the sender name. Set it to `"Developer Training Platform"`?
- [ ] `DailyLogReportController::details` repeats the whole filter query from `rows` (only the ordering and pagination differ). Extract the shared filter constraints (e.g. a `DailyLog` scope or a service method) when this controller is slimmed or moved to a Form Request?
- [ ] One method in `app/` still has an untyped parameter (closures are all typed now): `ScoringService::runningAverage($exceptVersion)` (`ScoringService::weekly()` and `summary()` were typed in the `ScoringReportController` Phase 3 batch; `carryForwardLabRecord($labRecords)` was typed when it moved to `ActivitySubmissionPageService` in Phase 4). - [ ] `ValidationLabController::artifact` (with the checks now in `ValidationLabService::blankArtifactInputErrors()`) still returns `back()->withErrors()` when the "Other" feature area / artifact type or the artifact name is blank after trimming. With the global `TrimStrings` and `ConvertEmptyStringsToNull` middleware, whitespace-only input already fails `required_if` / `required` in `StoreValidationArtifactRequest`, so these branches look unreachable. Remove them (or fold them into the Form Request) when the controller is slimmed in Phase 4?
- [ ] `MentorInterviewAvailabilityController::store` passes the validated `mentor_id` into `MentorInterviewAvailabilityService::create`, where `$data + ['mentor_id' => $mentor->id]` keeps the request's value. A coach who posts another coach's `mentor_id` therefore creates availability owned by that coach, and an admin who omits `mentor_id` gets a 500 (undefined array key). Drop `mentor_id` from the data passed to the service and make it `required` for admins?
- [ ] `POST /interviews/register` has both `throttle:5,10` route middleware and an in-request limiter (`StoreInterviewerRegistrationRequest`, 5 attempts per 600 s per IP). The middleware answers the sixth request with a 429 first, so the friendlier "Too many submissions" redirect is effectively unreachable. Keep one of them (drop the middleware for the redirect, or drop the in-request limiter)?
- [ ] `CoachReportService::dashboardStats()` (coach dashboard) loads every participant with `participants()` (six eager-loaded relations) and then loads them all again through `atRisk()`. The count is flat, but the work is done twice per page view. Reuse the first collection (or count at-risk participants with a query)?
- [ ] `CoachGateOverviewService::board()` (coach Gate board, moved from `CoachOperationsController::gates`) eager-loads `activitySubmissions` on every participant and `participant` on every Gate evaluation, but neither the service nor the view reads them. It also builds every Gate x participant row in memory before `CoachOperationsController::gates` paginates them. Drop the unused eager loads, and decide whether to paginate participants in the query?
- [ ] `CoachReportService::reportAtRiskRows()` (moved from `CoachOperationsController::reports`) filters the at-risk rows by mentor in memory, but `participants()` already applies the same `mentor` filter in the query, so the second filter never removes a row. Drop it?
- [ ] `SubmissionReviewService::record()` (moved from `CoachOperationsController::storeReview`) creates the review and then updates the submission status without a transaction, so a failed status update leaves a review whose decision the submission does not reflect.
